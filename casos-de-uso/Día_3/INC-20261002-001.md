## 2. Resumen ejecutivo

El Wazuh Manager dejó de arrancar correctamente el 1 de octubre de 2026, lo que provocó que el dashboard mostrara el error "API is down". Tras la investigación, se determinó que la causa raíz era doble: (1) el timeout de systemd era demasiado corto (45 segundos) para el tiempo de arranque del manager, y (2) la lista de IOCs `malicious-ip` tenía un formato incorrecto (IPs con dos puntos al final). Se aplicaron ambas soluciones y el manager volvió a funcionar correctamente el 2 de octubre a las 18:14 UTC.

## 6. Análisis

**Hipótesis evaluadas:**

1. **Fallo de red (Descartada):** El indexer y el dashboard funcionaban correctamente. El problema estaba en el manager.
2. **Corrupción de la base de datos (Descartada):** El indexer estaba `active (running)`. No había errores de datos.
3. **Timeout de systemd (Confirmada):** El manager tardaba más de 45 segundos en arrancar. Systemd lo mataba antes de que terminara.
4. **Lista de IOCs con formato incorrecto (Confirmada):** La lista `malicious-ip` tenía IPs con dos puntos al final, lo que impedía su carga y ralentizaba el arranque.

**Razonamiento:**

El manager de Wazuh carga muchas reglas, decodificadores y listas al arrancar. Si una lista tiene un formato incorrecto, el manager tarda más en procesarla (o falla directamente). En este caso, la lista `malicious-ip` tenía un formato inválido, lo que sumado a un timeout de systemd demasiado corto, provocaba que el manager nunca terminara de arrancar. La solución fue doble: aumentar el timeout y corregir el formato de la lista.

## 10. Lecciones aprendidas

- **Timeout de systemd:** Los servicios pesados (como Wazuh Manager) pueden necesitar más tiempo del que systemd les da por defecto. Es recomendable aumentar el timeout en producción.
- **Formato de listas de IOCs:** Wazuh espera un formato específico (una IP por línea, sin puertos ni dos puntos). Verificar siempre el formato antes de cargar listas.
- **Diagnóstico por capas:** Verificar el estado de cada componente (indexer, manager, dashboard) por separado ayuda a aislar el problema.
- **Documentación:** Tener un runbook de recuperación ahorra tiempo en futuros incidentes.
